Playbooks

A playbook is a YAML document describing a named remediation or verification made of command steps. The analyzer recommends a playbook by its id, and the safety guard decides whether it may run.

Example

id: restart-docker-unhealthy
title: Restart unhealthy Docker service
description: Restarts the Docker daemon when it is unhealthy.
risk: confirm
auto_run: false
applies_to:
  issue_ids:
    - docker_service_unhealthy
  hosts:
    tags:
      - docker
preconditions:
  - command: test -x /usr/bin/systemctl
steps:
  - id: restart
    command: systemctl restart docker
    timeout_seconds: 60
    idempotent: false
  - id: wait
    command: sleep 5
verifier_id: docker-service-healthy

Field reference

FieldMeaning
idUnique playbook identifier the analyzer targets.
titleHuman-readable name for the dashboard.
descriptionWhat the playbook does, shown next to incidents.
riskauto or confirm. Decides whether a run needs approval.
auto_runWhether the playbook is eligible to run without a click, subject to global auto mode.
verifiertrue marks a playbook as a verifier rather than a remediation.
verifier_idPlaybook id used to verify a remediation succeeded.
applies_to.issue_idsIssue ids this playbook is meant for.
applies_to.hosts.tagsHost tags the playbook applies to.
preconditions[]Commands that must succeed before the steps run.
steps[].idStep identifier used in the audit record.
steps[].commandShell command executed on the target host.
steps[].timeout_secondsPer-step timeout; enforced and capped by the safety guard.
steps[].idempotentMarks a step safe to repeat.

Bundled playbooks

These ship read-only inside the package and cannot be edited in place.

idRiskPurpose
sample-noopautoReads uptime and free -b as a demonstration.
sample-verifyautoVerifier that runs uptime; confirms the sample playbook ran.
restart-docker-unhealthyconfirmRestarts Docker when unhealthy, then hands off to the verifier.
docker-service-healthyautoRead-only verification that Docker is active and responding.

Bundled versus custom

  • Bundled — sourced from the package, read-only, flagged as builtin.
  • Custom — admin-authored playbooks are not authorable yet. The storage schema already reserves immutable revisions so an old incident can point at the exact version that ran once authoring lands.
No match, no run. If the analyzer names a playbook that does not exist, nothing executes; the incident is recorded instead. See Safety.
